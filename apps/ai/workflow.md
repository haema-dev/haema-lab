# 문서 색인 및 질문 처리 아키텍처

## [사전 작업] 문서 색인

> 배치 작업이며 유저 요청과 무관

### 0-1. 문서를 청크로 분할

* Django 관리 명령어 / CronJob을 사용해 문서를 청크로 분할한다.

### 0-2. 문서 청크 임베딩

```text
FastAPI /embed (kind=document)
        ↓
Node B
        ↓
문서 청크 벡터
```

* 문서 청크 벡터를 받는다.
* 이 과정은 **트랜잭션 밖**에서 수행한다.

### 0-3. 문서 및 벡터 저장

한 트랜잭션으로 다음 데이터를 저장한다.

* `source_document`
* `document_chunk`

  * 청크 내용
  * 청크 벡터

# [쓰기 1] Django API (동기)

## 1. 입력 검증

* 질문은 **300자 이하**여야 한다.
* 300자를 초과하면 즉시 에러 응답한다.
* 이 경우 DB 저장, 큐 등록, FastAPI 요청은 발생하지 않는다.

## 2. 중복 요청 확인

같은 유저가 동일한 질문을 다시 요청했는지 확인한다.

* 질문을 정규화한다.
* 정규화된 텍스트의 해시를 사용한다.
* 같은 유저 + 같은 질문 해시로 `queued` 또는 `running` 상태인 `job`이 존재하면:

```text
기존 job_id 반환
```

* 이 경우:

  * 새로 저장하지 않음
  * 큐에 넣지 않음
  * FastAPI 요청하지 않음

## 3. 최초 요청 저장

중복 요청이 아니라면 **한 트랜잭션**으로 저장한다.

```text
message
  - role = user
  - 질문 원문

job
  - status = queued
```

트랜잭션을 커밋한다.

> 커밋이 완료된 시점부터 다른 DB 연결(워커)에서 해당 데이터를 조회할 수 있다.

## 4. Redis 큐 등록

Redis 큐에 `job_id`만 전달한다.

```text
Redis Queue
    ↑
job_id
```

* 큐에 넣는 작업은 **여기서 한 번만** 수행한다.

## 5. 유저 응답

유저에게 다음을 반환한다.

```http
202 Accepted
```

```json
{
  "job_id": "..."
}
```

* 유저의 HTTP 요청은 여기서 종료된다.

# [쓰기 2] 워커 시작

## 6. Redis 큐에서 job 조회

워커가 Redis 큐에서 `job_id`를 꺼낸다.

## 7. Job 상태 변경

`job.status`를 다음과 같이 변경한다.

```text
queued → running
```

* 짧은 쓰기 작업이다.

## 8. 워커 진행

이후의 워커 처리 과정에서는 **DB 쓰기를 하지 않는다.**
또한 **DB 트랜잭션을 열지 않는다.**

---

## 9. 질문 임베딩

```text
FastAPI /embed (kind=query)
        ↓
Node B
        ↓
질문 벡터
```

* 질문 벡터를 받는다.
* 질문 벡터는 **워커 메모리에만 유지**한다.
* 이 시점에는 질문 벡터를 DB에 저장하지 않는다.

---

## 10. 유사 답변 검색

질문 벡터를 사용하여 `answer.question_embedding`에서 가까운 기존 답변을 검색한다.

---

## 11. 유사 답변이 있는 경우

유사 답변이 존재하면 해당 답변을 선택한다.

이 경우 다음 과정을 모두 건너뛴다.

* 근거 문서 검색
* 답변 생성
* 코드 검증
* LLM 판정
* fallback 생성
* FastAPI 생성 요청

그리고 **19번으로 바로 이동**한다.

---

## 12. 유사 답변이 없는 경우

유사 답변이 없다면 근거 문서를 검색한다.

질문 벡터를 사용하여 `document_chunk`에서 가까운 청크를 검색한다.

* 최대 5개 청크
* 전체 근거 길이 합계 최대 2,000자

```text
질문 벡터
    ↓
document_chunk 검색
    ↓
Top 5 청크
    ↓
총 2,000자 이하
```

---

## 13. 답변 생성

다음과 같이 FastAPI를 호출한다.

```text
FastAPI /generate
        ↓
Node B
        ↓
qwen3.5:27b
        ↓
답변 텍스트
        ↓
HTTP 응답
```

입력:

* 질문
* 근거 문서 5개

출력:

* 답변 텍스트

### GPU 동시성 제한

생성 요청은 GPU 세마포어로 감싼다.

```text
GPU 생성
  └─ 동시에 1개만 실행
```

---

## 14. 코드 검증

워커에서 `core/verify.py`를 사용하여 답변을 검증한다.

검증 항목:

1. 답변에 포함된 숫자가 근거에 존재하는지
2. 인용 ID가 12번 검색 결과에 존재하는지
3. 답변이 중간에 잘리지 않았는지

```text
답변
 ↓
core/verify.py
 ↓
통과 / 실패
```

* 이 단계에서는 FastAPI 요청을 하지 않는다.

### 검증 실패

코드 검증에 실패하면 **16번을 건너뛰고 17번 fallback으로 이동**한다.

---

## 15. LLM 판정

코드 검증을 통과하면 FastAPI `/judge`를 호출한다.

```text
Worker
  ↓
FastAPI /judge
  ↓
Gemini
  ↓
판정 결과
  ↓
Worker
```

판정 결과에는 **근거 없는 주장 목록**이 포함된다.

### 판정 통과

근거 없는 주장 목록이 비어 있으면 통과한다.

```text
[]
↓
검증 통과
↓
19번으로 이동
```

### 판정 실패

근거 없는 주장이 존재하거나 판정 자체가 실패하면 **17번 fallback으로 이동**한다.

---

## 16. 판정 실패

* 코드 검증을 통과했지만 LLM 판정에서 문제가 발견된 경우
* 또는 LLM 판정 자체가 실패한 경우

→ **17번 fallback으로 이동**

---

## 17. Fallback 생성

FastAPI `/fallback`을 호출한다.

```text
Worker
  ↓
FastAPI /fallback
  ↓
Gemini
  ↓
동일한 근거
  ↓
Fallback 답변
```

* 기존과 **동일한 근거**를 사용한다.
* Gemini가 fallback 답변을 생성한다.

Fallback 답변도 반드시 코드 검증을 수행한다.

```text
Fallback 답변
      ↓
core/verify.py
      ↓
통과 / 실패
```

### Fallback 검증 통과

→ **19번으로 이동**

### Fallback 검증 실패

→ **20번 실패 처리**

# [쓰기 3] 워커 종료

## 18. 워커 종료 처리

성공 또는 실패에 따라 최종 상태를 저장한다.

---

## 19. 성공 처리

성공하면 **한 트랜잭션**으로 저장하고 커밋한다.

### 19-A. 새로 답변을 생성한 경우

다음 데이터를 저장한다.

#### `answer`

* 답변 텍스트
* 모델명
* 검증 결과
* 9번에서 생성한 질문 벡터

#### `answer_citation`

* 답변에 사용된 인용 청크들

#### `message`

```text
role = assistant
answer = 새로 생성된 answer를 참조
```

#### `job`

```text
status = succeeded
```

즉:

```text
answer
 ├─ 답변 텍스트
 ├─ 모델명
 ├─ 검증 결과
 └─ 질문 벡터

answer_citation
 └─ 인용 청크들

message
 └─ answer 참조

job
 └─ succeeded
```

---

### 19-B. 유사 답변을 사용한 경우

11번에서 기존 유사 답변을 선택한 경우에는 새 `answer`를 생성하지 않는다.

또한 새 질문 벡터도 저장하지 않는다.

저장하는 것은 다음과 같다.

#### `message`

```text
role = assistant
answer = 기존 answer를 참조
```

#### `job`

```text
status = succeeded
```

즉:

```text
message
 └─ 기존 answer 참조

job
 └─ succeeded
```

---

## 20. 실패 처리

실패하면 `job`만 업데이트한다.

```text
job
 ├─ status = failed
 └─ failure_type = 실패 종류
```

다음 데이터는 저장하지 않는다.

* `answer`
* 질문 벡터

단, 질문 원문은 3번에서 이미 `message(role=user)`로 저장되어 있다.

# 재시도 정책

실패 종류에 따라 재시도 여부가 달라진다.

## 인프라 실패

다음과 같은 경우는 **재시도 대상**이다.

* 모델 서버 HTTP 5xx
* 연결 끊김
* `ErrorDeviceLost`
* Gemini 429

인프라 실패는 유저의 실패 카운터에 포함하지 않는다.

```text
인프라 실패
   ↓
재시도
   ↓
유저 실패 카운터 증가 없음
```

## 검증 실패

검증 실패는 **재시도하지 않는다.**

```text
검증 실패
   ↓
재시도 없음
   ↓
failed
```

# 완료 알림

DB 커밋이 완료된 후 Redis에 **"job 끝남" 알림**을 보낸다.

```text
DB COMMIT
   ↓
Redis
   ↓
"job 끝남"
```

> 이 Redis 메시지는 작업 큐가 아니라 **상태 알림**이다.

# 요약

## DB 쓰기

DB 쓰기는 다음 지점에서만 발생한다.

| 단계 | 작업                                                               |
| -- | ---------------------------------------------------------------- |
| 3  | `message(role=user)` + `job(queued)`                             |
| 8  | `job(running)`                                                   |
| 19 | 성공 시 `answer` + `answer_citation` + `message` + `job(succeeded)` |
| 20 | 실패 시 `job(failed)`                                               |

> 모든 DB 쓰기는 **Django에서 수행**한다.

---

## FastAPI 호출

FastAPI 호출은 워커에서만 수행한다.

| 단계 | Endpoint    | 용도             |
| -- | ----------- | -------------- |
| 9  | `/embed`    | 질문 임베딩         |
| 13 | `/generate` | 답변 생성          |
| 15 | `/judge`    | 답변 판정          |
| 17 | `/fallback` | fallback 답변 생성 |

FastAPI는 **요청을 받아 처리하고 HTTP 응답만 반환**한다.

---

## 벡터 저장

벡터 저장은 두 곳에서만 발생한다.

### 문서 색인

```text
0-3
source_document
document_chunk + 문서 청크 벡터
```

### 질문 처리

```text
19
answer.question_embedding
```

단, 질문 벡터는 **새로운 답변을 생성한 경우에만 저장**한다.

유사 답변을 사용한 경우에는 새 `answer`나 질문 벡터를 생성·저장하지 않는다.

> **답변 자체는 벡터로 만들지 않는다.**

---

## 큐

작업 큐 등록은 **한 번만** 발생한다.

```text
Django API
    ↓
Redis Queue
    ↓
job_id
    ↓
Django Worker
```

* 큐에 넣기: **Django API에서 1회**
* 큐에서 꺼내기: **Django Worker에서 1회**
* 작업 완료 알림: Redis를 사용하지만 **큐가 아닌 상태 알림**
